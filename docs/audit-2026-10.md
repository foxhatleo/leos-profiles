# Audit Report: `~/.leos-profiles`

**Scope:** HEAD `36e6ab1` on `master`, audited 2026-10-09 on macOS 27.0 arm64 with zsh 5.9.2.
**Method:** Nine audit lenses. Every finding was then checked by 1 to 3 adversarial verifiers. Severities shown are the final values after verification; where a verifier moved a severity, the original is noted.

---

## 1. Executive summary

**Verdict.** For a dotfiles and bootstrap repo, the engineering is well above average:
- Every direct download is pinned by SHA-256, and every git dependency by commit.
- GitHub host keys are cross-checked against the API.
- File writes are atomic, and the installer lock fails closed.
- The init-cache trust layer is hardened against tampering.
- Plugins load in the order each upstream recommends.
- shellcheck is clean, and the behavioural test suites pass locally under Bash 3.2.

Three problems undercut that:
1. **The documented onboarding path cannot finish on a fresh machine.** An AI agent runs `apply` without a TTY, so sudo, the Homebrew bootstrap and chsh cannot prompt.
2. **CI on `master` has been red for three weeks.** No branch protection stops red commits.
3. **Startup is about 220 ms (first prompt about 280 ms), and roughly half of that is the profile's own cache bookkeeping.**

**Top 5 things to fix**

| # | Fix | Finding(s) |
|---|---|---|
| 1 | Add a TTY/sudo preflight to `apply`. Have the AI give the user an exact `bash install.sh apply …` line to run in their own terminal instead of running it itself. | ONB-1 |
| 2 | Get CI green and keep it green. Find the root cause of "init cache is unsafe or unavailable" in the provisioning jobs, silence SC2317 or pin shellcheck, then add branch protection for the deterministic jobs. | CI-1, CI-2, CI-4 |
| 3 | Add a re-entrancy guard to `start.zsh` and a migration for the legacy unmarked loader. This machine will load the profile twice on its next reconcile. | ZSH-1 |
| 4 | Recover startup time: validate the cache dir once per shell, compute the cache key without a fork, `touch` the dump and move compaudit into the slow path, set `ZSH_AUTOSUGGEST_MANUAL_REBIND`. Projected startup is about 85 to 110 ms. | PERF-1, PERF-2, PERF-5 |
| 5 | Set `skip_global_compinit=1` in the managed `~/.zshenv`. On Debian and Ubuntu, zsh-completions and rbenv completions are currently lost in nearly every shell. | ZSH-2 |

**Strengths**
- **Supply chain:**
  - SHA-256 pinned artifacts are fetched with `--proto '=https' --tlsv1.2` and moved into place atomically after the digest matches.
  - Git dependencies are checked out at exact commits, and dirty checkouts are refused.
  - Plugins are pinned to reviewed commits, which is ahead of antidote and zinit.
- **Credentials:** keys are never uploaded, `known_hosts` is verified against `gh api meta`, and signing is enabled only after a real signed test commit.
- **Init-cache trust layer:** it checks the lexical and physical ancestor chains, ownership and modes, never evaluates output from a failed generator, and refuses to run as root against a user's cache. Adversarial tests cover it.
- **Load order:** zsh-completions → compinit → compdef registrants → fzf → fzf-tab → autosuggestions → syntax-highlighting last. The reasoning is written next to each step.
- **Avoided forks:** GOPATH is read from go's env file, GPG_TTY comes from `$TTY`, thefuck loads lazily, pyenv/rbenv use `--no-rehash` with a daily background rehash, and `brew shellenv zsh` names the shell explicitly.
- **Engine design:** a component registry with self-validation, postconditions that are re-verified rather than trusted from saved state, and a typed `inspect` plan.
- **Test quality:** shellcheck 0.11 is clean. Bash 3.2 compatibility holds apart from one bug (ONB-14). Tests use a sentinel pattern so they cannot pass without running their checks, and the cache tests are adversarial.

**CI-1. CI is red on master: real provisioning fails on 11 of 20 configurations the README lists as supported** (high)
- **Location:** `.github/workflows/ci.yml:189`
- **Evidence:**
  - The push run for 36e6ab1 (35546098659) and the scheduled runs on 09-21, 09-28 and 10-05 all failed. The previous merge (05a4188) was green.

- **Recommendation:** Treat this as a release blocker. Find the root cause of the init-cache refusal under `/tmp/leos-provisioning.*` (temp-dir ancestry or mode checks are the likely suspect). Otherwise, mark these configurations known-failing and update the README matrix.

### 3.2 Onboarding / setup

**ONB-1. The AI-run `apply` has no TTY, so sudo, the Homebrew bootstrap, chsh and passphrase prompts fail** (high)
- **Location:** `installer/packages.sh:9`. Also `packages.sh:28` (Homebrew installer), `config.sh:176-183` (`sudo tee /etc/shells`, `chsh`), `credentials.sh:184,278`.
- **Evidence:**
  - QUICK-INSTALL rule 10 has the agent run `bash install.sh apply --yes …`. Lines 19-24 only tell the user to "stay at the keyboard", and lines 9-11 forbid handing the user `install.sh`.
  - In the agent's shell, `[ -t 0 ]` is false, `/dev/tty` cannot be opened, and `sudo -n true` says a password is required.
  - Nothing in `installer/` or `install.sh` mentions `-t 0`, `/dev/tty`, `sudo -n` or `SUDO_ASKPASS`.
  - The pinned Homebrew installer switches to NONINTERACTIVE without a TTY and needs `sudo -n` to work. That comes from upstream's documented behaviour and was not run here.
  - CI uses NOPASSWD sudo with `--default-shell no --ssh skip --gpg skip`.
- **Impact:**
  - The primary flow fails on its main targets: a fresh Mac without Homebrew, and Linux without NOPASSWD sudo.
  - It works on a Mac that already has Homebrew and zsh as the login shell, because `ensure_sudo` returns early on macOS.
  - The saved profile makes the run resumable, but the resume goes through the same TTY-less agent.
- **Recommendation:**
  - Preflight with `sudo -n true` and `[ -t 0 ]` and emit manual-action records before making any change.
  - Have the agent give the user the exact `bash install.sh apply --yes …` line to run in their terminal, then parse its log.
  - Support `SUDO_ASKPASS`. Refuse `prompt` passphrases and chsh when there is no TTY.
  - Add a CI case with stdin from `/dev/null` and no NOPASSWD sudo.
- **Votes:** 3/3 upheld.

**ONB-2. Listing SSH/GPG keys needs scopes a default `gh auth login` lacks; the run hard-fails with a misleading error** (medium)
- **Location:** `installer/credentials.sh:76-77,238-239`
- **Evidence:**
  - Live token scopes are `gist, read:org, repo`. `gh api user/keys` returns 404 asking for `admin:public_key`, and `user/gpg_keys` asks for `admin:gpg_key`. The `X-Accepted-Oauth-Scopes` header also accepts `read:*`.
  - The installer `die`s with "check network and gh auth" (exit 1). Only `user:email` is mapped to an exit-3 manual action (:123-126).
  - Stubs always succeed.
  - A gap verifiers found: `provision_gpg` has no "refuse to replace" guard, so re-running `--gpg generate` after this failure creates a **second GPG key**.
- **Impact:**
  - The AI runbook gets exit 1 instead of a typed manual action. gh's own stderr does print the right `gh auth refresh` command.
  - Re-running SSH generate tells the user to switch to reuse (:180).
  - The behaviour is opt-in, since credentials default to Skip.
- **Recommendation:**
  - Map 403/404 to `manual-action github-key-scope` with `gh auth refresh -h github.com -s read:public_key,read:gpg_key`.
  - Document both scopes in QUICK-INSTALL.
  - Add the generate→reuse guard to the GPG path.
  - Add stub tests for scope errors.
- **Votes:** 3/3 upheld (high → medium).

**ONB-3. rbenv is installed without libyaml, so the first `rbenv install` of Ruby 3.x fails on Debian/Ubuntu/Fedora** (medium)
- **Location:** `installer/packages.sh:80` (apt dev-tools), `:87` (fedora)
- **Evidence:**
  - ruby-build forces `--with-ext=openssl,psych,+` (bin/ruby-build:731-734), and the 3.4.x definitions do not build libyaml themselves.
  - Neither `libyaml-dev` nor `libyaml-devel` is in the dev-tools lists.
  - Arch and macOS get libyaml only by accident, through the `ruby` package in `languages`.
  - gmp and autoconf are *not* required (finding corrected).
- **Impact:** A deterministic BUILD FAILED on two supported OS families. The error message is clear.
- **Recommendation:** Add `libyaml-dev`, `libyaml-devel` and `libyaml` (macOS/Arch dev-tools), plus a lightweight check that the package lists contain ruby-build's prerequisites.
- **Votes:** 3/3 upheld.

### 3.3 zsh integration

**ZSH-1. No migration for the legacy unmarked loader and no re-entrancy guard, so the profile loads twice after the next reconcile** (medium)
- **Location:** `installer/config.sh:55-79`, `zsh/start.zsh`
- **Evidence:**
  - Live `~/.zshrc` contains the unmarked `source "$HOME/.leos-profiles/zsh/start.zsh"` written by pre-faabab3 QUICK-INSTALL. Live `~/.zshenv` starts with `# leos-profiles zshenv`.
  - `install_managed_block` strips only its own markers, then appends.
  - No `__leos_loaded`-style guard exists. `inspect` reports `zsh-config needed`.

### 3.4 Performance

**PERF-1. Init-cache bookkeeping takes about 45% of startup** (medium)
- **Location:** `zsh/cache.zsh:66,69,113,117-121,300`
- **Evidence:**
  - Every `__leos_init_cache` call re-runs `__leos_cache_dir`. That forks `$(umask)` (0.8 ms), runs an unconditional `mkdir -p` (2.7 ms) and does 4 ancestor zstat walks. Then `printf | sha256sum` forks (3.7 ms).
  - zprof: `__leos_cache_dir` 12 calls, 56–62 ms; `__leos_init_cache` 10 calls, 92 ms inclusive (43%).
  - A zoxide cache hit takes 14.7 ms against 3.0 ms to run `zoxide init` directly.
  - Prototypes: memoizing the directory brought startup to about 150 ms; adding a fork-free key brought it to 109 ms.
- **Impact:** About 80–100 ms of a 220 ms startup. For fast native generators the cache is slower than regenerating.
- **Recommendation:**
  - Validate once per shell and memoize the result in a global, keeping the same checks.
  - Use `[[ -d ]]` before `mkdir`. Remove the umask subshell.
  - Compute the key in-process (identity header or sidecar file).
  - Have `__leos_rehash_daily` check its stamp before calling `__leos_cache_dir`.
  - Optionally stop caching generators that run in under 6 ms.
- **Votes:** 3/3 upheld (high → medium).

**PERF-2. The daily compinit fast path is effectively dead after day one, and compaudit forks on every shell** (medium)
- **Location:** `zsh/interactive.zsh:39,43-46`
- **Evidence:**
  - compinit never rewrites a valid dump, so its mtime stays old and `(#qN.mh-24)` never matches again until the fpath file count changes. Reproduced with a backdated dump.
  - `insecure=$(compaudit)` at line 39 runs before the branch.
  - Timings: audit 9.1 ms, full compinit 20 ms, `-C` 4.8 ms.
  - The live dump was recently rewritten, so here the slow path is intermittent rather than permanent.
- **Impact:** About 25–30 ms per shell, which defeats the documented "regenerate at most once a day" design.
- **Recommendation:** Use `if [[ -n $dump(#qN.mh-24) ]]; then compinit -C …; else insecure=$(compaudit); …; compinit -i -d $dump; touch $dump; fi`, as Prezto does. Add a test that backdates the dump.
- **Votes:** 3/3 upheld (high → medium).

**PERF-3. pyenv/rbenv cost about 58 ms per shell with no versions installed** (medium)
- **Location:** `zsh/path/pyenv.zsh:12`, `rbenv.zsh`
- **Evidence:**
  - The cached pyenv init begins with `PATH="$(bash --norc -ec …)"` (about 11 ms fork), then sources the legacy `compctl -K _pyenv pyenv` completion (about 8 ms module load).
  - `path/pyenv` takes 37–42 ms and `path/rbenv` 17–19 ms. Most of rbenv's cost, and half of pyenv's, is cache-wrapper overhead (PERF-1).
  - `~/.pyenv/versions` and `~/.rbenv/versions` are empty.
  - `--no-push-path` removes the bash fork.
- **Impact:** About 25% of startup.
- **Recommendation:**
  - Use `pyenv init --no-rehash --no-push-path - zsh` plus a zsh-native `path=($PYENV_ROOT/shims ${path:#…})`, which keeps the shims-first order.
  - Drop compctl in favour of compsys.
  - Optionally lazy-load when no versions are installed.
- **Votes:** 3/3 upheld (one verifier argued for low).

**PERF-4. Measured latency is 5 to 6 times zsh-bench targets** (medium)
- **Location:** `zsh/interactive.zsh:1` (imprecise; the main cost is in `cache.zsh`)
- **Evidence:**
  - First prompt in a pty: 261–299 ms against a 50 ms target. Command lag: median 32–48 ms against 10 ms.
  - Per-Enter breakdown: direnv 5.7 ms, autosuggest rebind 7.5–10.6 ms, Starship about 20 ms in a git repo.
  - The docs disclaim any guarantee and record 189.9 ms, and today measures about 240 ms.
- **Impact:** New tabs and every Enter feel slow. Part of the lag is inherent to the Starship choice.
- **Recommendation:** Fix PERF-1, PERF-2, PERF-5, PERF-6 and PERF-3 first. Then consider zsh-defer or an instant prompt. Target under 100 ms first prompt and about 20 ms lag.
- **Votes:** 3/3 upheld (one verifier argued for low).
